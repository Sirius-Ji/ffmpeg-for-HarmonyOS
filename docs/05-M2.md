# M2：把 PCM 喂到扬声器

> 状态：**M2 收官**（2026-11-04）。8 音阶样例与 192 kHz/2ch 大文件 FLAC 均真机通过：
> 无变调、无卡顿、无爆音，position 正常，underflow 极低。

## 第四轮：修掉"用字符串嗅探判错"（2026-11-04）

现象：选 192 kHz/2ch FLAC，status 里 `durationMs`（253735）和 `srcRate`（192000）都对，
`error` 是空串，UI 却显示"解码器打开失败"，`playerPlay` 从没被调用（所以没有 perf、没有声音）。

根因：ArkTS 侧用 `openRes.includes('"error"')` 判断成败，而 `StatusJson()` **永远**带一个
`"error":"…"` 字段（没错误时是空串）——于是每一次"打开成功"都被判成失败。
和 192 kHz、和 swr、和 OHAudio 都没关系（那一步压根没走到）。

修法：`player*` 系列 NAPI 统一返回结构化结果，上层只看布尔：

```ts
// d.ts
export interface NapiResult { ok: boolean; data: string; }
```

```cpp
// napi：成功 {ok:true,data:<status json>}；失败 {ok:false,data:{"error":"..."}}
```

教训（写进契约，别再犯）：**不要用"响应里有没有某个字段"判断成败**。要么给状态码，
要么给显式布尔字段。JSON 里带 `error:""` 这种"永远存在"的字段，做包含判断必然误伤。

## 第三轮：文件选择器 + 大文件（2026-11-04 晚）

### 选歌不复制文件

`DocumentViewPicker` 返回的是 URI 不是路径，而且应用没有对应目录路径的长期读权限。两条路：
复制进沙箱（几十 MB 的 FLAC 要白占一份空间）或者拿 fd 直读。选了后者：

```
DocumentViewPicker.select() → uri
  → fs.openSync(uri, READ_ONLY) → fd
  → native playerOpenFd(fd)（内部 dup，返回值到手后 ArkTS 立刻 close 自己的 fd）
```

解码器侧新增 `AudioDecoder::OpenFd()`：`dup` 一份 fd，自建 `AVIOContext`（`read` + `lseek` 回调），
`avformat_open_input(nullptr)` 配 `AVFMT_FLAG_CUSTOM_IO`。`Close()` 里按 FFmpeg 的规矩释放
`avio->buffer` → `avio_context_free` → `close(fd)`。

### 长时间运行的稳定性

| 参数 | 值 | 原因 |
| --- | --- | --- |
| 环形缓冲 | 2 秒（384 KB） | 抵抗 IO 抖动；大文件顺序读偶尔会被调度打断 |
| 解码块 | 8192 帧（≈170 ms） | 减少唤醒次数与 ring 竞争 |
| 预填充 | 200 ms 后再 Start 渲染器 | 启动阶段不欠载 |
| 填充策略 | ring 不满就继续解，留 4 KB 余量 | 水位始终高，回调几乎不会取空 |

另外把"补静音"和"系统欠载"彻底分开：`gaps` 是我们补的次数，`underflow` 来自
`OH_AudioRenderer_GetUnderflowCount`。

### 性能日志

解码线程每 2 秒打一行（HiLog，tag `FFM1`）：

```
[player] perf decode_avg=0.045ms/frame calls=312 cpu=18% rss=48213KB ring=180KB written=12288KB
```

- `decode_avg`：平均每帧解码耗时（含 swr 重采样）
- `cpu`：进程累计 CPU / 墙钟（`getrusage` 增量），可能 >100%
- `rss`：`/proc/self/statm` 常驻内存
- `ring`：当前缓冲水位；长期贴 0 说明供数吃紧
- `written`：已解码并写入 ring 的总字节

同样的数字也进 `playerStatus()` 的 JSON（`decodeAvgUs` / `cpuPercent` / `rssKb`）。

### 大文件验收建议

> 实测记录（2026-11-04）：192 kHz / 2ch FLAC，时长 253 秒，走 picker → fd → 播放，
> 全程无卡顿、无爆音，`positionMs` 正常，`underflow` 极低。

1. 点"选歌播放"，选一首几十 MB 的 FLAC；
2. `hdc hilog | findstr FFM1` 观察 `[player] perf` 行：
   - `decode_avg` 对 FLAC 应该在 0.1 ms/frame 量级（软解 + 重采样）
   - `rss` 应稳定（不随播放时长单调上涨）
   - `ring` 应在 100 KB 以上波动，偶尔贴近 0 但不应长期为 0
3. 状态里的 `underflow` 和 `gaps` 全程应为 0 或个位数；
4. 听感：不应有爆音、断续、变调。

## 第二轮修复：供数结构与自证（2026-11-04 晚）

第一轮修了时间戳与 EOF 行为，但"播放被拉长 / 疯狂卡顿"这件事仍然只是推断。这一轮做两件事：
**结构上把供数做稳**，**把数据正确性变成设备上能读的数字**。

| 改动 | 说明 |
| --- | --- |
| 环形缓冲 1 s → **2 s**（384 KB） | 回调块如果偏大，1 s 缓冲会出现"每轮都差一点"的系统性欠载 |
| 解码块 2048 → **8192 帧**（≈170 ms） | 一次多解一点，减少线程唤醒与 ring 竞争频率 |
| **预填充再启动** | `Play()` 先起解码线程，等 ring 攒到 200 ms（或 800 ms 超时）再 `OH_AudioRenderer_Start`，消灭启动阶段的必然欠载 |
| 填充策略 | 解码线程改为"尽量填满（留 4 KB 余量）"，不再等掉到 75% 水位才补 |
| 位置口径 | `positionMs` = `OH_AudioRenderer_GetFramesWritten / 48000` 并 clamp 到 duration；另加 `audioMs` = 真实从 ring 取走的音频字节换算（不含补的静音） |
| 欠载口径 | `underflow` 用系统 `GetUnderflowCount`；`gaps` 是我们补静音的次数，两者分开 |
| 自检升级 | 流式路径解**两遍**：A 按源采样率/声道（校验样本数有没有被放大/缩小），B 按 48k/2ch（与桌面参考哈希对拍） |
| 诊断字段 | `maxCallbackBytes` / `rendererFrameSize` / `srcRate` / `pcmSrcBytes` 全部进 status JSON |

自检里 A 路的意义：如果真出现"数据被拉伸 3.2 倍"，那么按源参数解出来的字节数会是
`duration × srcRate × srcCh × 2` 的 3.2 倍，`[player] selfcheck src=... bytes=... expect~...` 这行会当场暴露。
不用再靠听感推断。

## 第一轮真机现象与修复记录

现象：低沉拖长的"嘟——"、`positionMs` 冲到 16000+（源只有 5 秒）、`underruns` 121。

排查后的三个结论：

1. **测试音频本身就会听成"嘟"**：旧样例 `test.m4a` 是 440 Hz + 880 Hz 双音持续 5 秒，
   在平板上外放就是电话忙音的质感，根本没法判断"对不对"。
2. **position 暴涨是代码问题**：旧实现里解码线程 EOF 后，OHAudio 回调仍在每次填静音并累加
   `playedBytes_`，渲染器也不停 → 位置 = 回调总时长（5 秒音乐 + 11 秒静音 = 16 秒）。
3. **underruns 口径是错的**：旧实现把"我们自己补静音"当欠载计数；121 次 ≈ 尾部静音的回调次数，
   不一定是解码跟不上。系统自己有 `OH_AudioRenderer_GetUnderflowCount`，应该用它。

修复内容：

| 问题 | 修法 |
| --- | --- |
| 位置虚高 | 改用 `OH_AudioRenderer_GetFramesWritten`（官方口径）并 clamp 到 `durationMs` |
| EOF 后继续输出 | `decoderEof && ring 空` 时回调**返回 0**，不写静音、不推进位置 |
| 欠载口径混乱 | 系统欠载用 `GetUnderflowCount`，自己补静音的次数单独记为 `gaps` |
| 配置可能没生效 | 每个 `Set*` 检查返回值；`GenerateRenderer` 后用 `Get*` 回读 rate/ch/fmt/enc/frameSize，不一致直接报错 |
| 无法判断数据对错 | 新增自检：用流式路径整解一遍，算 FNV-1a 64 + 峰值，打 `[player] selfcheck` |
| 样例听不出对错 | 新增 `play.m4a`：8 音上行音阶（C5→C6），3.6 秒，峰值 15926 |

## 新样例的桌面参考值（用于对拍）

`play.m4a` 用桌面 ffmpeg `-ar 48000 -ac 2 -f s16le` 解出的 PCM：

| 项 | 值 |
| --- | --- |
| PCM 字节 | 691200（3.6 s × 48000 × 2ch × 2B） |
| 峰值 | 15926 |
| FNV-1a 64 | `f661e8e3e9b99eaf` |

设备上 `[player] selfcheck` 打出来的 `pcm/peak/hash` 应该与这三项一致；不一致就说明解码/重采样路径有问题，
先别怀疑 OHAudio。


## 一个必须先纠正的认知

"OHAudio 同步模式"这个说法不存在。NDK 里 `libohaudio.so` 没有 `OH_AudioRenderer_Write` 这类阻塞写接口，
音频输出只有**回调**模型：

| 接口 | 引入版本 | 语义 |
| --- | --- | --- |
| `OH_AudioStreamBuilder_SetRendererCallback` | 10（已废弃） | 老的回调结构体 |
| `OH_AudioStreamBuilder_SetRendererWriteDataCallback` | 12 | 往 `audioData` 填满整块 PCM，返回结果枚举 |
| `OH_AudioStreamBuilder_SetRendererWriteDataCallbackAdvanced` | **20** | 可以只填一部分，返回**实际写入字节数**（0 表示让回调线程睡一会） |

我们基线是 API 20，所以用 **Advanced 版**：能精确告诉系统"这块我只填了 N 字节"，
环形缓冲快空的时候可以少写、避免把静音当数据算进时钟。

真正有"同步模式"的是 `OH_AudioCodec`（API 20 起 `OH_MD_KEY_ENABLE_SYNC_MODE`），那是 M3 的解码侧，不是播放侧。

## 架构

```
ArkTS (Play/Stop)
   │  NAPI
   ▼
AudioPlayer
   ├─ AudioDecoder (流式 ReadPcm)  ── 解码线程：av_read_frame → avcodec → swr
   │        └── 输出 S16LE / 48 kHz / 2ch
   ├─ RingBuffer (1 秒, mutex 保护)
   └─ OH_AudioRenderer ── 音频回调线程：FillAudio() 从 ring 取，缺口补静音 + 计 underrun
```

关键参数：

| 项 | 值 | 为什么 |
| --- | --- | --- |
| 输出格式 | S16LE / 48 kHz / 2ch | 固定输出，renderer 配置不用跟着源变；44.1k 源在 swr 里重采样 |
| 环形缓冲 | 192 KB（1 秒） | 手机音频回调周期 ~10–20 ms，1 秒足够抵消解码抖动 |
| 解码块 | 2048 帧（8 KB） | 比回调块大，单次 swr 调用摊薄开销 |
| 欠载策略 | 补静音 + `underruns++` | 不推进"假装有数据"，但也不让音频时钟停；用计数观察质量问题 |

## NAPI 接口

| 函数 | 说明 |
| --- | --- |
| `playerOpen(path)` | 打开文件 + 建 renderer，返回状态 JSON |
| `playerPlay()` | 启动 renderer + 解码线程（若上一轮已播完，自动重开文件从头播） |
| `playerPause()` | `OH_AudioRenderer_Pause` |
| `playerStop()` | 停线程 → Stop/Flush → 清空缓冲，状态回 `stopped` |
| `playerStatus()` | `{state, positionMs, durationMs, underruns, finished, sampleRate, channels, codec, error}` |
| `playerRelease()` | 释放 renderer 与解码器 |

M2 是**单实例**（一个进程一个播放器），接口里没做句柄，够验证链路，也方便以后包成对象。

## 真机上怎么验（第二轮）

```bash
# 签名安装后，点 Play，听声音；同时看日志
hdc hilog | findstr FFM1
```

预期输出（关键六行）：

```
I FFM1 : [player] renderer rate=48000 ch=2 fmt=1 enc=0 frameSize=...
I FFM1 : [player] selfcheck src=44100/2 bytes=635040 expect~635040 hash=...
I FFM1 : [player] selfcheck out=48000/2 bytes=691200 expect~691200 peak=15926 hash=f661e8e3e9b99eaf
I FFM1 : [player] open ok codec=aac duration=3600ms pcmBytes=691200 hash=f661e8e3e9b99eaf
I FFM1 : [player] preload ring=38400 bytes, eof=0
I FFM1 : [player] decode loop end, pcm=691200 bytes, eof=1
```

验收判据：

1. **先看 selfcheck 两行**：
   - `src=44100/2` 的 `bytes` 必须 ≈ `expect~`（差几个 AAC 尾帧正常）。**如果 bytes 是 expect 的两三倍，
     说明样本数被放大**——这才是"播放被拉长"的硬证据。
   - `out=48000/2` 的 `bytes/peak/hash` 必须与 691200 / 15926 / `f661e8e3e9b99eaf` 一致。
2. **再听声音**：8 个音从低到高（C5→C6），每个音约 0.45 秒，总共 3.6 秒。
3. `positionMs` 从 0 涨到 ~3600 就**停住**（clamp 到 duration），不再继续爬。
4. `underflow` 是 0 或个位数；`gaps` 在播放期间不应持续增长。
   `maxCallbackBytes` 和 `rendererFrameSize` 会告诉我们系统一次要多大块。
5. 点 Stop 立刻静音；再点 Play 从头重播（内部会重新 open 文件）。

## 已知限制（M2 故意不做）

- 无 seek、无进度条拖动，播完只能重开
- 无后台播放、无音频焦点/打断处理（来电、其他应用抢焦点时会怎样还没测）
- 单实例，多文件切换要重新 `playerOpen`
- 固定 48 kHz 输出，44.1 kHz 源有重采样
- 播完后回调返回 0、渲染器不自动 Stop（省得在回调里调 Stop 死锁）；要彻底释放点 Stop
